# ADR 0002: Pulse v0.3 Effect Reliability and Task Semantics

- Status: Accepted
- Target version: 0.3.0
- Scope: Pulse effect delivery, asynchronous tasks, and durable operations

## Context

Pulse must distinguish three kinds of work that have different delivery and lifetime guarantees:

- a foreground instruction that is useful only to the current UI;
- process-local asynchronous work that eventually proposes a mutation;
- an operation whose outcome must survive process death, retries, or a UI subscription gap.

Treating all three as effects makes loss, replay, cancellation, and ownership ambiguous. Treating all
three as tasks incorrectly implies that an in-memory coroutine is durable. This decision specializes
the runtime guarantees in [ADR 0001](./0001-v0.3-runtime-ordering.md).

## Decision

### 1. Work is classified before it is scheduled

| Kind | Purpose | Lifetime and delivery | Examples |
|---|---|---|---|
| `UiEffect` | One-shot instruction for the currently active UI | Replay zero; delivered only through the active UI coordinator | Navigation, toast, focus, transient prompt |
| Task | Process-local asynchronous work that can propose mutations | Owned by the keyed task registry; governed by an explicit task policy and execution token | Request, computation, debounce, refresh |
| Durable operation | Work or acknowledgement that must survive process death or a subscription gap | Represented by durable state and an operation identifier, with persistence or an external scheduler | Persistent sync, resumable upload, acknowledged command |

A `UiEffect` never represents business completion or required persistence. A process-local task never
claims process-death durability. Durable work may use tasks while the process is alive, but its source
of truth is durable state rather than the task instance.

### 2. UI effects have one delivery coordinator

Each store permits at most one active `UiEffect` coordinator. The coordinator owns one foreground
delivery session; arbitrary consumers cannot independently subscribe to the effect stream.

The delivery contract is:

1. replay is zero: a new session receives no effect emitted before that session started;
2. effects are delivered in transition order and in FIFO order within the session;
3. the active path has bounded capacity and applies backpressure when that capacity is exhausted;
4. an effect is never silently dropped;
5. without an active coordinator, the effect is discarded and an `UndeliveredUiEffect` failure is
   reported;
6. ending a session clears its pending effects and reports each one as undelivered;
7. one consumer failure is isolated, reported as a typed failure, and cannot stop the frame processor
   or other controlled consumers.

Buffer capacity is runtime configuration. Changing the capacity cannot change replay, ordering, or
the prohibition on silent loss.

### 3. Tasks are keyed and policy-driven

All long-running process-local work runs through a keyed task registry. Every execution receives a
token, and mutation emission is available only through the token-bound `IntentContext`.

The registry supports exactly these policies:

- `Latest`: invalidate and cancel the current execution for the key, discard pending work for that
  key, and run the newest request;
- `DropWhileRunning`: keep the current execution and reject a new request while that key is running;
- `Queue(capacity)`: run one execution per key, preserve FIFO order, and retain at most `capacity`
  pending requests;
- `Parallel(maxConcurrency)`: run at most `maxConcurrency` requests independently, each with its
  own token;
- `Conflate`: keep the current execution and at most one pending request, replacing the pending
  request with the newest one.

`PulseTasks.launch` reports admission immediately as `Accepted`, `DroppedWhileRunning`, `QueueFull`,
`ParallelLimitReached`, or `Closed`. An accepted result owns a narrow `TaskHandle` with a stable
request identifier and one suspending `awaitOutcome` operation. The handle exposes no coroutine job,
deferred, channel, or scope.

Every accepted request completes exactly once as `Completed`, `Replaced`, `Cancelled`, `Closed`, or
`Failed`. Replacement distinguishes `Latest`, conflated-pending replacement, and a policy change.
This includes requests that were admitted to a queue but never started. Over-capacity queue and
parallel requests, `DropWhileRunning`, and a closed registry remain immediate rejections and
therefore create no handle. `cancel(key)` invalidates one key; `cancelAll()` invalidates every key
owned by the Store.

Task lifecycle observation is deliberately attached to the admitted request's `TaskHandle` instead
of a second global task-event stream. This keeps completion lossless and correlated while avoiding a
new buffering and multi-subscriber reliability contract. Non-fatal task failure and late mutation
also enter the store's typed failure path. Applications that need durable start/completion history
model it as operation state rather than depending on a process-local diagnostic stream.

The task outcome describes process-local execution, not durable business acknowledgement.
Applications still represent business completion that must survive process death through state and
a durable operation model.

### 4. Cancellation invalidates mutation authority

Token invalidation happens before cancellation or replacement becomes externally visible. After a
token is invalid, every mutation attempt from that execution is rejected as a late mutation and is
reported through the runtime failure channel.

`CancellationException` is control flow. Framework guards rethrow it and never map it to a failure
mutation or a `UiEffect`. The task handle maps policy replacement to `Replaced`, explicit or
task-local cancellation to `Cancelled`, and owner or store closure to `Closed`; none produces a
domain failure by itself.

Non-fatal task failures are reported through the typed failure channel. An executor may deliberately
map a non-cancellation failure to a domain mutation only while its token remains valid.

Closing the store invalidates all task tokens, cancels running work, and discards pending work
according to the ordered close cutoff. A domain-level `operationId` is still required when stale work
must be rejected across process or machine boundaries.

### 5. Durable operations use durable state and acknowledgement

An operation that must survive process death has a stable identifier and an explicit state machine,
including any required acknowledgement. Persistence or a platform scheduler owns resumption.

The runtime does not convert a `UiEffect` into durable delivery and does not persist coroutine jobs,
task tokens, pending task requests, effect envelopes, or coordinator sessions. Reconstructing a
process restores durable state; it does not replay transient UI instructions.

### 6. Module boundaries

- `mvi-core-contract` defines `UiEffect`, effect envelopes, `TaskKey`, `TaskPolicy`, `TaskToken`,
  `TaskLaunchResult`, `TaskHandle`, task outcomes, reducer outcomes, and typed failures without
  implementing scheduling.
- `mvi-core-runtime` defines `PulseTasks` and owns the effect coordinator, bounded delivery, task
  registry, token validation, and close behavior.
- Platform modules provide scopes, dispatchers, lifecycle sessions, and durable-state adapters. They
  do not redefine task or effect semantics.
- Application code classifies work, chooses a task key and policy, and defines durable operation
  state. It cannot bypass token validation to emit mutations.

## Required verification

The reusable runtime test suite must cover:

- replay-zero behavior with no coordinator and across coordinator replacement;
- single-coordinator enforcement, FIFO delivery, bounded backpressure, and undelivered diagnostics;
- all five task policies, including bounded queue/parallel rejection, observable replacement,
  queueing, conflated-pending behavior, and `cancelAll`;
- token invalidation before replacement, cancellation, and close;
- rejection of late mutations;
- cancellation that produces neither a failure mutation nor a `UiEffect`;
- isolation of task and effect-consumer failures;
- durable state restoration without restoring tasks or UI effects.

## Consequences

- UI-effect loss is explicit and diagnosable rather than hidden behind callback timing.
- Task concurrency is a declared feature policy instead of ad hoc loading flags and jobs.
- Cancellation cannot be mistaken for a business failure.
- Work that requires durability must model durability explicitly; Pulse remains a process-local state
  runtime rather than a durable workflow engine.

# ADR 0005: Bound the complete Split admission path

- Status: Accepted
- Target version: 0.4.0
- Scope: `PulseSplitStoreViewModel`

## Context

Pulse 0.3 bounded the Core Store mailbox and the Split executor channel independently. A UI frame
could leave the Core mailbox and block while publishing to a full executor channel. At the same
time, the active executor could block while sending a mutation back through the Core Store. The two
bounded stages therefore formed a capacity cycle even though neither stage was unbounded.

The same design also made `trySend` report only Core mailbox pressure. It could return `Enqueued`
while the complete UI-to-executor path was already saturated.

## Decision

`PulseSplitStoreViewModel` uses one fair permit budget, equal to `mailboxCapacity`, for each UI intent
from Split admission until its executor decision terminates. A permit is released exactly once on
normal completion, executor failure or cancellation, undelivered channel input, Store rejection,
admission failure, caller cancellation, or ViewModel close. A small atomic lease state machine
distinguishes pending, Core-claimed, executor-transferred, cancellation-requested, and released
ownership. Cancellation before executor transfer releases immediately or at the transfer boundary;
after transfer, executor cleanup remains the only permit owner.

- Suspending `send` waits for a permit and remains the backpressure path.
- Non-suspending `trySend` returns `Full` when no end-to-end permit is available.
- `REJECT_AND_REPORT` publishes a coalesced `SplitAdmissionOverflow` diagnostic.
- `callbackIngress` requires a handler for every non-enqueued result.

The Core mailbox remains independently bounded because mutations and lifecycle commands still use
it. The Split permit is an outer UI in-flight bound, not a replacement mailbox or a second runtime.

## Consequences

At most `mailboxCapacity` UI intents can be executing or waiting for the serial executor, so the
executor channel always has enough capacity to receive every admitted UI frame. The executor can
therefore send a mutation without participating in a channel-capacity cycle.

The contract does not promise that a bounded non-suspending call accepts every event. Applications
that cannot suspend must handle `Full` and lifecycle rejection, then apply an explicit domain loss,
coalescing, retry, or resynchronization policy.

## Rejected alternatives

- An unbounded executor channel hides pressure and violates the bounded-runtime invariant.
- Dropping or conflating UI intents in the framework assigns domain meaning the runtime does not
  know.
- Increasing both independent capacities postpones the same cycle.
- A second callback runtime or application FIFO gate duplicates ordering and cleanup ownership.

# ADR 0003: Pulse v0.3 Android Lifecycle, Ownership, and Saved State

- Status: Accepted
- Target version: 0.3.0
- Scope: `mvi-platform-android` and `mvi-platform-android-compose`

## Context

The core runtime is thread-safe and platform-neutral, but Android adds stricter ownership and
delivery rules. Reducer work and UI delivery must reach the main thread regardless of the caller;
tasks must be cancelled with their ViewModel; Compose collection must follow lifecycle state rather
than composition presence; and process recreation must not be confused with configuration change.

This decision binds the runtime contracts from [ADR 0001](./0001-v0.3-runtime-ordering.md) and the
effect and task contracts from [ADR 0002](./0002-v0.3-effect-reliability.md) to Android.

## Decision

### 1. ViewModel scope is the production default

The Android adapter uses `viewModelScope` as its production task owner. A scope and dispatchers are
injectable through the ViewModel construction path so tests can use controlled scheduling and
virtual time.

The adapter owns only the child work it creates. Closing Pulse cancels its task registry and child
jobs; it does not cancel an externally supplied parent scope. Production cleanup remains aligned
with Android's ViewModel lifecycle.

Task policies and token validation remain runtime concerns. The Android layer supplies execution
resources but does not implement a second task registry.

### 2. Reducer and UI delivery obey the Main rule

`send` and `trySend` may be called from any thread. The Android adapter marshals ordered engine work
onto the configured Main dispatcher.

The following run on that dispatcher:

- reducer execution and committed-state publication exposed to Android UI;
- lifecycle-aware selector evaluation and delivery;
- active `UiEffect` coordinator delivery;
- Android-facing failure callbacks.

Task bodies may use an explicitly selected worker dispatcher. Their mutation attempts return to the
ordered engine and cannot update UI state directly.

### 3. ViewModel closure is final and idempotent

`PulseSplitStoreViewModel` has a `final onCleared` implementation that calls the Pulse close path
exactly once. Subclasses of the v0.3 entry point cannot replace this cleanup. The legacy
`PulseViewModel` keeps its v0.2 overridable surface for source and binary compatibility; existing
subclasses that override `onCleared` must continue to call `super.onCleared()`.

New subclasses place optional cleanup in `onPulseCleared`; the framework invokes that hook only
after establishing its final close path.

The close path:

1. establishes the engine admission cutoff;
2. invalidates task tokens and cancels owned task work;
3. ends the active UI-effect session and diagnoses pending undelivered effects;
4. closes runtime and platform subscriptions;
5. remains safe when invoked more than once.

Callers that must observe completion use the runtime close barrier. Android's non-suspending
`onCleared` establishes cleanup; it does not create an alternative blocking shutdown protocol.

The ordered Store still drains frames admitted before its cutoff. Split Intent execution is
owner-bound platform work rather than part of that Store frame: `trySend` reports admission, not
executor completion, and close may cancel an executor that has not started or finished. The Android
`awaitClosed` barrier completes only after both the Store drain and all adapter-owned jobs have
finished cancellation cleanup.

### 4. State collection is lifecycle-aware and selector-based

Compose state collection requires an explicit `LifecycleOwner` and is active only while that owner
is at least `STARTED`.

A selector maps root state to the value needed by a UI region. Selected values use equality-based
distinct delivery by default. On entering `STARTED`, the binding selects from the current committed
state; while stopped, it delivers no updates. Restarting does not replay intermediate values, but it
does expose the latest selected value.

Full-state collection is the identity-selector convenience case and follows the same lifecycle
rules. Disposing the composition always detaches the lifecycle binding.

### 5. UI-effect collection owns a lifecycle session

Compose effect collection also requires an explicit `LifecycleOwner`. Entering `STARTED` opens the
store's single coordinator session; leaving `STARTED` ends it and diagnoses pending effects as
undelivered.

The binding has replay zero. An effect emitted before the session, while stopped, or between owners
is not replayed after restart or configuration change. A second active coordinator for the same
store is rejected and diagnosed rather than receiving duplicate effects.

The effect callback runs on the configured Main dispatcher. Composition disposal and lifecycle stop
are both sufficient to end the binding, and repeated cleanup is idempotent.

### 6. ViewModel and lifecycle owners are explicit

Every ViewModel acquisition requires an explicit `ViewModelStoreOwner`, key, and factory. Framework
helpers do not silently fall back to an Activity, Fragment, navigation entry, or composition local.
The owner and key together determine ViewModel identity.

Every Compose selector and effect binding requires an explicit `LifecycleOwner`. The lifecycle owner
may differ from the ViewModel owner; the call site makes that choice visible.

Factories consume `CreationExtras` so default arguments and saved-state ownership remain available.
Configuration change reuses the ViewModel from its `ViewModelStoreOwner`; it does not reconstruct the
store through saved state.

### 7. Saved state is opt-in and state-only

`PulseSavedStateAdapter<S>` is optional. It converts between a committed Pulse state and values supported
by `SavedStateHandle`; Pulse does not require every state to implement `Parcelable` or
`Serializable`.

When configured:

- restoration completes before the engine admits inputs;
- only committed state is checkpointed;
- adapter keys, schema versions, and migrations are explicit application responsibilities;
- restoration failures are reported through the typed state-restoration failure channel and never
  produce a partially restored state;
- the binding chooses either `FALLBACK_TO_INITIAL_STATE` or `FAIL_CREATION` for ordinary restore
  failures.

Saved state never contains task jobs, task tokens, pending task requests, effect envelopes,
coordinator sessions, transition subscribers, or other process-local runtime objects. Work that must
resume after process death follows the durable-operation model from ADR 0002.

### 8. Module boundaries

`mvi-platform-android` owns:

- ViewModel binding and final cleanup;
- production and injected execution environments;
- explicit `ViewModelStoreOwner` acquisition and `CreationExtras` handling;
- the optional `PulseSavedStateAdapter` integration.

`mvi-platform-android-compose` owns:

- lifecycle-aware full-state and selector collection;
- lifecycle-managed access to the single UI-effect coordinator;
- Compose disposal and callback freshness.

Application code owns feature selectors, owner selection, saved-state schemas, task keys and
policies, and durable operation state. It does not create a parallel scope, task registry, or effect
queue around Pulse.

## Required verification

The Android and Compose test suites must cover:

- background-thread `send` and `trySend` with reducer, selector, effect, and failure callbacks on
  Main;
- production `viewModelScope` ownership and injected scope and dispatcher behavior;
- final, idempotent `onCleared` cleanup and close-barrier completion;
- admitted-frame drain versus owner-bound executor cancellation at the close boundary;
- task cancellation and late-mutation rejection during ViewModel clearance;
- selector behavior across `STARTED` and `STOPPED`, including equality-based distinct delivery;
- effect session start and stop, replay zero, coordinator uniqueness, and undelivered diagnostics;
- configuration change with stable ViewModel identity and no duplicate effect delivery;
- explicit owner isolation and reuse for equal and unequal owner and key pairs;
- saved-state round trips, schema migration, restoration failure, and process recreation;
- public API visibility that prevents UI code from obtaining a mutation sink or backing Split store.

## Consequences

- Android callers can send from any thread without moving reducer or UI delivery off Main.
- Cleanup of the v0.3 `PulseSplitStoreViewModel` entry point cannot be bypassed by subclasses.
- Compose subscriptions stop with lifecycle state instead of remaining active merely because the
  composition exists.
- Owner selection and process-restoration behavior are visible at the call site.
- Saved state restores committed state only; transient work and UI instructions remain transient.

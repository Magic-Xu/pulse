# ADR 0001: Pulse v0.3 Runtime Ordering and Public API

- Status: Accepted
- Target version: 0.3.0
- Scope: Pulse framework modules

## Context

Pulse 0.2 serializes reducer execution and state assignment with a monitor, but publishes state,
effects, plugin callbacks, and lifecycle changes outside that single ordering boundary. Concurrent or
reentrant dispatch can therefore expose a different order from the committed state order. The same
design also leaves callback failures, cancellation, close cutoffs, and UI-effect delivery undefined.

Pulse 0.3 establishes one runtime engine and keeps the 0.2 API as a compatibility facade over that
engine. Correct ordering is the primary constraint; convenience APIs and state-decomposition DSLs
must build on the finished engine.

## Decision

### 1. One ordered engine

Each store owns one bounded input admission gate, one FIFO mailbox, and one frame processor.
Inputs and lifecycle control messages share that mailbox. No reducer, plugin, state callback, effect
callback, or executor may recursively invoke the processor.

For an accepted input, the processor performs this sequence:

1. allocate a contiguous `sequenceId`;
2. read `stateBefore`;
3. invoke the reducer;
4. normalize and commit `stateAfter`;
5. update the public `StateFlow` before publishing the frame;
6. publish the `TransitionFrame`;
7. publish or explicitly diagnose each `UiEffect`;
8. complete the caller's `TransitionResult`.

Concurrent callers only compete for mailbox order. Reentrant sends are queued after the current
frame and never execute in the current callback stack.

### 2. Admission, cancellation, and close

`send` uses suspending backpressure. `trySend` only reports whether the input was enqueued; it does
not imply reducer completion. A full mailbox returns `EnqueueResult.Full` from `trySend` and never
silently drops input.

Every admitted input receives a monotonic `requestId`. A caller cancelled before its input starts
marks that input cancelled; the processor skips it without assigning a transition sequence. Once
reduction starts, the frame completes independently of caller cancellation.

`close` first establishes an atomic admission cutoff, then queues an ordered close control message.
Inputs admitted before the cutoff drain in order; later inputs are rejected. The non-suspending
`close()` call establishes the cutoff. `awaitClosed()` is the completion barrier used by tests and
coordinators that must wait for the drain to finish.

### 3. State and reducer outcomes

`StateFlow<S>` is the only new-API current-state source. A reducer returns one of:

- `Changed(state, uiEffects)`: the input produced a candidate state;
- `Unchanged(uiEffects)`: the input was handled without a state change;
- `Ignored(reason)`: the input was deliberately inapplicable and produces no state or effect.

`Changed` with a state equal to the current state is normalized to `Unchanged`. Equal state is not
re-emitted, while every processed frame remains visible on the transition stream.

The 0.2 `Reducer` and `Next` types remain binary-compatible. A legacy reducer is adapted inside the
runtime; it is not a second engine.

The legacy callback adapter follows the same equality normalization: an equal state does not invoke
legacy state observers or legacy plugin state hooks, while the accepted intent and its transition
remain observable.

### 4. Failures

Framework guards catch non-fatal `Exception` only. `CancellationException`, `VirtualMachineError`,
`ThreadDeath`, and `LinkageError` are never converted into Pulse failures.

Every reported failure carries the owning `storeId` in `FailureContext`. Request, sequence, state
revision, input type, component, and thread metadata are attached when the observing boundary knows
them; application-owned values cross the handler boundary only through the configured redactor.

Reducer failure does not commit state or publish effects. Controlled callback boundaries report
typed failures independently:

- reducer;
- legacy state consumer;
- UI-effect consumer;
- plugin;
- executor;
- mailbox overflow;
- undelivered UI effect;
- late mutation;
- state restoration.

One consumer or plugin failure cannot stop other consumers or the mailbox processor. The default
error handler reports redacted metadata to standard error; it is not silent.

### 5. Transition and plugin model

`TransitionFrame` contains request and sequence identifiers, state revision, input, before/after
state, normalized outcome, UI-effect envelopes, timing, dispatcher, mailbox depth/high-water, and
optional reducer failure.
Plugins receive immutable completed frames through `onTransition` and failures through `onFailure`.
They cannot mutate or veto a frame.

Legacy plugin callbacks remain available through an adapter and are isolated from the processor.

### 6. UI effects

`UiEffect` is restricted to foreground, one-shot UI instructions. The new stream has replay zero and
one active coordinator. Without a coordinator, effects are discarded with an
`UndeliveredUiEffect` diagnostic. During an active session, delivery is FIFO with bounded
backpressure. Ending the session clears pending effects and diagnoses each undelivered envelope.

Business work, persistence, and operations that must survive a subscription gap are not UI effects.
They run as tasks and return mutations, or are represented as durable state plus acknowledgement.

### 7. Split intent and tasks

The public Split ViewModel surface exposes only `send(UI)` and `trySend(UI)`. Mutation emission is
available only through an `IntentContext` owned by the executor. UI code cannot obtain the backing
store or construct an accepted mutation input path.

Long-running work is managed by a keyed task registry with `Latest`, `DropWhileRunning`, bounded
`Queue(capacity)`, bounded `Parallel(maxConcurrency)`, and `Conflate` policies. Each execution
receives a token. Cancellation or replacement
invalidates the token, so late mutation emission is rejected and diagnosed. Domain-level
`operationId` remains necessary for data consistency beyond a process-local task.

### 8. Platform boundaries

- `mvi-core-contract` contains markers, reducer outcomes, frames, failures, and legacy contracts. It
  has no Android or coroutine runtime dependency.
- `mvi-core-runtime` contains `PulseStore`, mailbox processing, flows, effect coordination, tasks,
  runtime configuration, and legacy adapters.
- `mvi-platform-android` binds the engine to ViewModel scope, injectable dispatchers, explicit
  owners, and optional saved-state adapters.
- `mvi-platform-android-compose` contains lifecycle-aware state selectors and UI-effect collection.
- `mvi-extensions` contains `StateLens`, state-decomposition helpers, and optional DSLs.
- `mvi-testing` contains public probes, virtual-time helpers, and the reusable Store TCK.

### 9. Legacy compatibility

The published 0.2 interfaces, class names, constructors, and artifact coordinates remain present.
No abstract member is added to the legacy `Store` interface.

Legacy `dispatch` blocks until its frame completes. Legacy state and effect callbacks run on an
isolated serial delivery context, preserving frame order and allowing callback reentrancy to enqueue
work without entering the reducer stack. `start`, `stop`, and `close` map to ordered engine control
messages. Deprecated APIs point to the new API or migration guide.

## Consequences

- Correctness no longer depends on callers choosing a thread or avoiding reentrancy.
- A slow transition subscriber or active UI-effect coordinator can apply intentional backpressure.
- New APIs are coroutine-based; legacy synchronous calls pay a blocking compatibility cost.
- State-decomposition and ViewModel convenience APIs must be finalized after the runtime and task
  contracts, not before them.
- Pulse does not provide distributed exactly-once delivery or a durable workflow engine.
